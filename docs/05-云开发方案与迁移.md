# 云开发方案与迁移

域名备案期间，后端先放在微信云开发上；备案通过后再迁到自有服务器。两套后端并存于同一个仓库，小程序页面只有一份。

## 1. 目录怎么分

| 目录 | 作用 | 什么时候用 |
|---|---|---|
| `cloud/functions/api/` | 云开发后端：一个云函数，内容数据打包在函数里，用户数据存云数据库 | 现在 |
| `server/` | 自有服务器后端：Fastify + PostgreSQL | 备案通过后 |
| `miniapp/` | 小程序，只有一份代码。构建时选择连哪个后端 | 一直 |

两套后端的接口路径和返回结构完全一样，所以页面不用改。切换点只有一处：`miniapp/src/utils/request.ts`。

| 构建命令 | 连接的后端 | 产物目录 |
|---|---|---|
| `npm run build:cloud` | 云函数 `api` | `miniapp/dist/cloud` |
| `npm run dev:mp-weixin` | 本机 `127.0.0.1:3000` | `miniapp/dist/dev/mp-weixin` |
| `npm run build:mp-weixin` | `https://api.iopenai.tech` | `miniapp/dist/build/mp-weixin` |

## 2. 云开发能省什么、不能省什么

- **省掉的**：域名、域名备案、HTTPS 证书、服务器运维。登录也省了，微信直接把用户身份带给云函数。
- **省不掉的**：小程序自身的备案仍然要办，通过后才能发布。
- **费用**：云开发现在没有长期免费额度，基础套餐按月收费（我了解的是每月 19.9 元左右，以开通页面显示为准）。这个小程序的用量远在基础套餐之内。

## 3. 开通与部署步骤

需要你本人操作，全部在微信开发者工具里完成。

1. 把真实的小程序 AppID 填进 `miniapp/src/manifest.json` 的 `mp-weixin.appid`。测试号 `touristappid` 不能用云开发。
2. 在 `miniapp` 目录执行 `npm run build:cloud`。
3. 开发者工具导入 `miniapp/dist/cloud`。
4. 点工具栏的「云开发」，按提示开通并创建一个环境。
5. 如果创建了不止一个环境，把环境 ID 填进 `miniapp/.env.cloud` 的 `VITE_CLOUD_ENV`，重新执行第 2 步。只有一个环境可以留空。
6. 在左侧文件树里右键 `cloudfunctions/api`，选「上传并部署：云端安装依赖」。等待提示成功。
7. 点「编译」。首页能显示科目和文言文卡片，就说明通了。

三个数据库集合 `users`、`favorites`、`history` 会在云函数第一次运行时自动创建，不用手工建。集合权限保持默认即可，小程序端不直接读写数据库，全部经过云函数。

每次改了云函数代码或数据文件，都要重新执行第 2 步和第 6 步。

## 4. 两套后端的差别

| 项 | 云开发 | 自有服务器 |
|---|---|---|
| 内容数据 | 打包在云函数里，启动时载入内存 | PostgreSQL 表 |
| 搜索 | 内存里逐句匹配（815 句，足够快） | SQL `LIKE` |
| 用户身份 | 微信直接提供 openid | 小程序 `wx.login` → 服务端换 openid → 签发 token |
| 用户数据 | 云数据库三个集合，都带 `openid` 字段 | `users`、`favorites`、`search_history` 三张表 |
| 历史记录的 id | 字符串 | 数字 |
| 限流 | 无（靠云开发自身的配额） | 每 IP 每分钟 120 次 |
| 首次请求 | 冷启动时会慢 1 秒左右 | 无冷启动 |

核心逻辑在 `cloud/functions/api/core.js`，有独立的测试：在项目根目录执行 `node --test cloud/test/core.test.mjs`。测试用例与 `server/` 的接口测试对应，用来保证两边行为一致。

## 5. 备案通过后怎么迁

1. 按《上线清单》第二、三节部署自有服务器，确认 `https://api.iopenai.tech/health` 正常。
2. 导出用户数据：云开发控制台 › 数据库，把 `users`、`favorites`、`history` 三个集合各导出为 JSON。
3. 导入 PostgreSQL。三个集合都以 openid 标识用户，对应关系是：
   - `users._id` → `users.openid`，同时带上 `nickname`、`last_subject`、`last_read`
   - `favorites.{openid, kind, ref, created_at}` → 先按 openid 找到 `users.id`，再写入 `favorites`
   - `history.{openid, q, created_at}` → 同上，写入 `search_history`

   导入脚本到迁移时再写，那时才知道实际的数据量和导出格式。
4. 执行 `npm run build:mp-weixin`，上传新版本并提交审核。
5. 新版本发布后，老版本的用户仍在调用云函数，所以云函数和云数据库要保留一段时间。这段时间里老版本用户新增的收藏不会自动同步到新后端；发布后隔一两周再做一次第 2、3 步的增量导入，然后停掉云开发。

同一个小程序下，云开发拿到的 openid 和自有服务器通过 `jscode2session` 拿到的 openid 是同一个值，所以用户迁移后不需要重新登录，生词本能对上。

## 6. 这套方案没有验证过的地方

云函数的核心逻辑在本地测过，小程序也能按云开发模式编译出来。但下面这些必须在真实的云环境里才能确认：

- `cloud/functions/api/index.js` 里对云数据库的读写。
- 小程序里 `wx.cloud.callFunction` 的调用和返回。
- 集合自动创建是否生效。

第一次部署后请走一遍主流程（搜索、字词详情、收藏、生词本、历史），有报错把云函数日志里的内容发给我。
